vLLM / NVFP4 / PLE映射 ↗DGX Spark专用方案把大块查表参数映射至NVMe；写作与编辑是两套运行方案，维护补丁、权重和缓存条件。

ik_llama.cpp ↗CPU专家计算与GPU混合卸载核对具体架构、量化内核、CPU指令与MTP配置；没有本期每台整机的统一跑分。
KTransformers ↗CPU与GPU异构计算专家已有相关Qwen-Next路线；本期资料未证实本期3.8 Flash-Next的完整适配，先核对支持清单。
exo / 多卡 / 外接显卡 ↗分摊容量与计算多台容量可分担，互联不是本地内存带宽。计入雷雳、网卡、OCuLink或PCIe的实际配置及附件成本。
PowerInfer / FlexGen ↗专用稀疏预测或分层吞吐对应专用模型或研究任务；未取得本期权重加速证据，不把其他模型的成绩移到这张选购表。
Android / Vulkan / NPU ↗手机与低功耗设备核对芯片、可用内存及应用后端；NPU的TOPS不代表可以直接运行任意GGUF。

Section 02 · Internals
底层原理：五个概念，够你预测瓶颈
这部分知识不过期，但下面的具体数字全部换成了我自己机器上量出来的口径。
🗂️
GGUF 文件格式
GGUF（GGML Unified Format）是 llama.cpp 定义的二进制格式，2023 年替代旧版 GGML，解决了向后兼容和元数据问题。

文件结构：GGUF（4 字节魔数）→ 版本号 → 张量数量 → 键值元数据（模型名 / 架构 / 超参数）→ 张量索引 → 量化后权重数据。

关键优势：单文件包含所有信息；支持 mmap 内存映射，按需加载；量化信息嵌在文件里，框架自动识别精度。
🔢
量化（Quantization）
权重本质是浮点矩阵。FP32 → FP16 → INT8 → INT4 逐级砍精度换体积。Q4_K_M 里的 K 表示混合量化策略（每个张量按重要性用不同位宽），M 表示中等偏上的档位。

量化先减少权重体积，再用你的任务检查结果。不同模型、量化算法与任务的影响不同；同一位宽也可能混合不同精度。这里不把未经对应任务验证的“质量保留百分比”写成实测结论。
🧮
KV Cache
注意力机制要缓存 K 和 V，公式是 2 × 层数 × KV 头数 × head_dim × 上下文长度 × 2 字节。

我用 Qwen3-8B 的官方 config.json 核对过：每个 token 约 144 KiB（= 2×36×8×128×2）。32K 窗口就是 4.83GB——比模型文件本身还接近。这就是为什么"上下文开大一点"很贵。
🧱
GPU 分层（-ngl）
显存不够时，把一部分层留在 CPU。-ngl 99 表示全部层都上 GPU（我的实测都是这个配置）。

代价直接来自带宽差：DDR5 约 60–80 GB/s，RTX 4070 是 504 GB/s，Apple 统一内存实测裸读 287 GB/s。部分层掉回 CPU，速度可能掉一个数量级。
📐
上下文长度
上下文越长，KV Cache 越大，带宽被摊薄，生成越慢。这不是玄学，是显存占用曲线。

我在同一台机器、同一份 Qwen3-8B Q4_K_M、llama.cpp 上扫过一遍：上下文从 0 加到 32768，生成速度从 54.5 掉到 28.0 词元/秒，腰斩。
🧱
Prefill 与 Decode
Prefill（读提示词）能并行，吃算力；Decode（逐 token 生成）只能一个一个来，吃内存带宽。

所以「预填充 3218 tok/s、生成 133 tok/s」这种组合很正常——两者瓶颈根本不是同一个东西。我的 9 个小模型实测里，预填充比生成快一到两个数量级。

Section 03 · Formats
模型格式怎么选
同一个模型，格式不同，能装进你机器的型号就完全不同。
格式典型体积（27B 级）需要什么谁在读它结论
.gguf 16.8 GB（Q4_K_M） 单文件 + mmap llama.cpp 默认选择。支持按层在CPU与GPU间安排计算；混跑能否顺手要看具体模型、内存和后端
.safetensors 55.6 GB（BF16） 文件容器；实际加载和卸载方式由引擎决定 vLLM / MLX 需核对BF16或量化版本，扩展名本身不决定精度和内存需求
GPTQ / AWQ 约 14 GB NVIDIA 卡 + 专用内核 vLLM 先核对模型架构、内核、系统与对应GPU支持
MLX量化模型目录 约 17 GB（4bit） Apple Silicon mlx_lm 通常包含safetensors、配置和分词器；下载后核对目录与模型架构
EXL2 约 12 GB EXL2 专用内核 exllamav2 位宽与具体模型包决定体积，需对应专用运行时
💡
三条选择规则，够用。先确认参数放在显存、统一内存还是主机与SSD，再按目标上下文计算缓存和运行缓冲，最后用真实任务比较速度。顺序反了，你会花时间调一个根本装不下的模型。
Section 04 · Quantization
量化档位：质量 vs 体积
先按具体文件安排容量，再用同一任务比较结果；不提供跨模型通用的质量保留百分比。以下为本期收集的文件与部署口径。
本期模型包文件体积／安排选型时检查什么
Qwen3.8 27B常规四比特约16～19GB；片中样例约16.46GB权重外预留上下文、视觉与运行缓冲，按实际文件核对
Qwen3.8 Flash-Next常规四比特本期资料约94～111GB核对分支、查表参数与引擎的驻留安排
Flash-Next Splash原版Q2_0主权重与DFlash2配套，64GB平台有开发者记录较低比特与草稿加速分别影响质量、内存和速度
Flash-Next MTPLX Optimized Speed动态4bit，注意力投影8bit；专用包按开发者内存要求选择；第一次读取与缓存预热后续问分开
Qwen3.5 9B／4B四比特片中样例约5.68GB／2.74GB适合先在已有电脑、手机或开发板验证；实际可用内存与后端单独核对
⚠️
有一个例外要单独说：三值化。我测 Ternary-Bonsai-2-27B 的 PQ2_0，模型文件压到 5.9GB（1-bit 版本 3.9GB），但写出来的内容有一半是错的。「装得下」和「能用」在极低位量化上是两回事——低到某个点之后，压缩省下的内存换不回质量。
Section 05 · Production Command Lines
真正在跑的命令行
下面两条是方寸智匣生产环境实际拼出来的启动命令（来自它的后端实现），也是我这半年所有实测用的参数。每个开关后面写它为什么存在。
llama.cpp b10705 · Metal
$ llama-server \ --model <模型路径> \ --host 127.0.0.1 --port <端口> \ --alias <显示名> \ --ctx-size <按内存算> \ --parallel 1 \ --reasoning auto --reasoning-budget -1 \ --ctx-checkpoints 8 --checkpoint-min-step 0 \ --jinja --no-webui \ --cache-type-k q8_0 --cache-type-v q8_0 -fa on \ # 有独显时追加 -ngl <全部层数> \ # 视觉模型追加 --mmproj <投影文件> \ # 稀疏 MoE 模型追加 --fit off # -ngl 99 = 整模型上 GPU # --fit off = 不要自动缩减上下文去迁就内存 # --reasoning budget -1 = 不限制思考长度
MLX · mlx_lm.server
$ mlx_lm.server \ --model <模型路径> \ --host 127.0.0.1 --port <端口> \ --chat-template-args '{"enable_thinking": false}' \ --max-tokens <输出上限> \ --trust-remote-code \ --prompt-cache-bytes <提示缓存字节数> # 环境变量：HF_HUB_OFFLINE=1（离线） # OMP_NUM_THREADS=1
开关作用踩过的坑
--prompt-cache-bytes限制提示缓存上限，防止多轮对话把 KV Cache 撑爆不加会在第 2 轮 OOM：Insufficient Memory。我加 8GB 上限后，第 2 轮从 3 分钟变成 2 秒
--chat-template-args关掉模型的思考模式Gemma 系列检测到 system 消息会自动开思考，输出全被 占满，看着像模型坏了
--cache-type-k/v q8_0KV Cache 量化，内存减半必须同时加 -fa on（flash attention）。不开 q8 时一个 -fa 都不传——llama.cpp 默认 auto 更准
--ctx-checkpoints定期存检查点，长任务中断能续不开的话长任务一崩全没了
--reasoning思考模式开关llama.cpp 侧现在用这个；--chat-template-args 是 mlx_lm 侧的做法，两边参数不通用
--max-kv-sizeKV 上限（token 数）只有 mlx_vlm 认这个。mlx_lm 用的是 --prompt-cache-bytes（字节数），混用直接启动失败
⚠️
关于「命令里的模型路径」。我的 AI-Models/Language-Models/GGUF/ 和 /MLX/ 在 2026-10-21 实扫时是空的，权重都清到方寸智匣的受管目录去了。上面的命令用 <模型路径> 占位，是因为路径会随你把模型放在哪儿而变——但下面那几行的参数是真的，照抄就能用。

Apple 机型的可用内存是系统放给 GPU 的那部分（macOS 默认留 5.73GB / 12.71GB），不是标称内存。Windows 侧数字来自 2026-10 那次 8GB 显卡实测，显存峰值 7850 MiB、系统内存峰值 26.39 GiB。

💡
为什么 8GB 显存的机器能跑 35B？因为 MoE 模型把专家权重放在系统内存里按需调用——显存只装激活路径。代价是这部分要走 PCIe 来回搬。完整拆解在 完全免费，Windows 下 8GB 显卡跑 Qwen 35B。
Section 09 · Two Modes
同一份权重，两种活法
大模型放内存有两种方式：整份常驻，或者只把精确需要的那部分放进 SSD 模式。
指标完整常驻32GiB 精确 SSD
启动到就绪40.39 秒8.98 秒
引擎登记驻留44.20 GiB31.21 GiB
全机 1 秒采样峰值57.08 GiB44.59 GiB
短题首字 / 总耗时0.43 / 4.01 秒1.39 / 5.88 秒
长材料题首字 / 总耗时2.46 / 4.99 秒4.90 / 8.10 秒
重复材料题0.26 / 2.68 秒0.27 / 2.87 秒

重复问同一段材料时两边几乎一样——因为第二次会命中 2595 个输入缓存 token。所以规律很清楚：日常用 SSD 模式，起步快、省 13GB；只有需要连续追问同一个大上下文时才值得常驻。

完整数据在 方寸智匣接入 Sushi；另一个常被忽略的开关是 --lazy-mode（llama.cpp 0.4 新增），开启后权重按需加载，能明显压低常驻占用。
