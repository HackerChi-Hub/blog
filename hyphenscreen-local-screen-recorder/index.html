1.8.0：动画到底做完了没有，统计也要看得明白

模型说“准备写入”，对话就结束，时间线上却只有一部分内容；换到ChatGPT订阅，动画做出来了，速度和用量又不完整。这一版把两件事一起处理：完成状态要对照工程，统计要对照实际收到的数据。

打开AI面板，每轮请求从等待、接收结构、调用工具到结束，都保留过程记录。用时、首个输出、正文与公开的思考、接收均速、工具次数，以及本次输入和整轮累计词元使用同一套显示。ChatGPT订阅也能收到服务实际回传的用量、缓存命中和思考词元；没有公开的内容会写明未提供。完成后再次输入，发送按钮可用，重新打开聊天仍能看记录。

这里的“接收均速”按通道实际到达的字符增量计算，排除了工具执行和每次首段等待，单位是字符/秒。服务可能先攒一部分再发过来，所以这个数字适合观察当前请求是否在输出，不能直接当成电脑跑模型的推理速度。“本次输入”是最近一趟请求携带的内容，“本轮累计”则把多次工具往返相加，就像单次快递重量和一天寄件总重，应该分开看。

创建动画时，软件会核对真正写入的场景、片段和明确给出的时间范围，发现缺段会在原等待期限内自动补做，最多两次。工具参数出错会显示具体字段；反复失败或没有进展会明确结束，已经写入的内容保留。修正同一场景、同一位置也不会再叠出重复片段，人工裁剪仍受保护。

MiniMax M3.1 Flash的思考档位现在实际传到接口，原始思考、签名与工具消息完整保留。实际验证中，ChatGPT与Poe完成了三场生成和一次收尾追加；MiniMax写完追加场景后遇到服务错误，软件保留结果，继续后完成核对。本地Sushi长任务这次只做完两场，第三场还没完成，记录保留了错误结构与超时原因。需要复杂故事时，模型本身仍要选合适。

1.7.9：动画做好就保存，用量也说清楚

这次遇到的现象很直接：模型一直在思考，点了停止，动画却立刻出现在时间线上。查记录后发现，场景早已写入成功，后面还在反复读取、检查和重写；旧版一直等整轮请求结束，才把结果交给编辑器。1.7.9把这一步提前了：每次有效修改都会逐次显示和保存，后续核对继续进行。停止或结束再返回同一份结果，不会重复应用；手工编辑与切换工程仍有冲突保护。

重复上下文也一起处理。以前只查一次动画列表，就可能把工程里所有旧场景的完整结构又发给模型；现在先给场景索引和写入回执，需要具体细节时再按图层读取。完整关键帧、曲线和原始记录仍在，没有靠删减动画或强行缩短输出来省时间。同题Sushi只读核对中，末次请求的实际输入从72,593降到26,294词元，约减少63.8%。两轮缓存命中和工具次数不同，这个数字说明的是本次输入负担减少，不是动画生成速度的同比提升。

用量显示现在分三处看：顶部是完整请求估算或最近一次服务实际输入，底部是本轮所有调用的累计；自动探测的上下文窗口会在新请求前核对，手填值保留。旧对话没有记录过的实际输入不会倒算。场景和片段也按实际ID计数，同一场景改两次不再报成两个场景。

1.7.8：看清动画怎么做，也能直接接入Poe

动画已经写进时间线，聊天里却还在等待，最容易让人以为整个任务卡住了。这一版把制作过程收成一个工作台：先看当前阶段，需要细查再展开工具记录。模型提交的原生场景结构、工具参数、返回结果都能查看和复制，场景写入后继续报告实际图层数与时长。参数预览表示模型打算做什么，工具结果才表示实际做了什么；导出与播放仍分别检查。

Poe也成为独立平台。在AI设置中选择Poe，填写自己的官方API密钥，再从实时目录选择模型。软件按文字输出、工具能力和支持端点筛选，不把图片或视频机器人混进剪辑模型列表；读目录不消耗生成请求。当前账号能否使用某个型号，可以点击“测试连接与工具调用”确认。我这次用实际Poe账号完成工具往返，并做出一个3秒、2图层的原生场景。小型测试模型曾猜错内部风格编号；先明确读取目录后完成，复杂作品仍需要合适的模型和具体要求。

本地任务超时或触及输出上限后，下一次发送或点击“继续生成”会按需自动整理早期对话，不必先手动压缩。原始聊天和已写入工程的动画保留，摘要无效时继续使用原历史。独立测试中，模型使用的历史估算从6841降到1904词元，自动整理后继续回复成功；整个过程包含后续模型请求，并不是摘要本身的耗时测试。

连接状态也不再计作思考文字。本地兼容服务的思考字段能正确读取；界面区分字符平均接收速度、对话文字估算和服务实际返回的词元。对话栏只有几百词元，并不代表工具定义和系统指引也只有这么多。动画聊天续作会沿用动画等待设置，MiniMax按所选区域读取官方最新目录。源码回归4742项通过、2项跳过。Mac已安装，609个文件及链接与构建产物一致，严格签名及品牌检查通过；正式安装版接口读回场景并导出3秒1080p30动画，完整解码通过。桌面读取凭据时遇到钥匙串认证，随后取屏工具报系统错误，最后的界面点击验收尚未完成。Windows／Linux保留实际1.8.0。

1.7.7：把实时数据的口径和输出上限一起修正

1.7.6 的实时数据有两个口径问题，这一版修掉：输出字数只算正文，思考过程单独显示为“思考 N 字”；速度按正文与思考合计计算，模型先思考、中间插入工具调用时，不会再显示成接近零的“0.2 字/秒”。模型服务只上报输出词元时显示“词元 出 N”，不再把未上报的输入写成“0 入”。

输出上限也一起调了：Anthropic 接口（MiniMax 等）单次输出从 16384 提到 20000 词元，本地模型提到 32768，两者都能用环境变量覆盖。所有提供方遇到 max_tokens／length 截断都会明确停止，并保留已经产生的思考、工具结果和文字，不再只回一句 Empty response from model。动画提示词也要求模型控制单个场景的体积，过大就拆成多个场景，先说一句计划就调用工具。

1.7.6：对话留下过程，没跑完的也能接着做

模型干活时最难受的不是慢，而是不知道它在干什么、慢在哪里。这一版在输入框上方常驻一排本轮数据：状态、用时、首字延迟、输出字数与速度、工具调用次数和上下文用量。模型服务真的上报了词元用量，才显示词元数；没上报就不编。

“本轮制作过程”也从一段会被不断覆盖的文字，改成带时间戳的记录：读取上下文、写第几个场景、场景回读结果、每次工具完成或失败，都在列表里。这段记录和模型的思考过程现在写在消息上并保存在本机，切换会话、压缩上下文或者重启软件之后，仍然可以展开回看。

没跑完的回合不再只剩一句报错。已经产生的思考、文字和工具结果会保存成一条“未完成 · 可继续”的消息，点“继续生成”就从这里接着做，已经写进工程的部分照旧保留。

上下文也不再固定只带20条消息。本地服务能报出窗口时（方寸智匣、llama.cpp、vLLM、LM Studio 都行）自动读取，读不到可以在 AI 设置里手动填写；接近窗口85%时在发送前自动压缩较早的对话。压缩只改变发给模型的历史，不删除对话记录和思考过程。往上翻历史也不会再被流式输出拉回底部；切到“媒体”“录制”标签时制作进度继续在跑，切回“编辑”还在。

“制作动画”弹窗也一起收了尾：等待设置从整条强调色横幅收成一行可展开的设置，关闭按钮从28像素无底色改成36像素带描边，并补上“连续长卷”的作用与细节控制说明——连续长卷是让所有分镜共享同一世界、镜头沿动作推进，细节仍由口播分段、时长和“自定义要求”决定。

先讲一件让我后背发凉的事。我给自己写的录屏软件做了自动打码——识别画面里的邮箱、密钥这些东西，盖上马赛克。功能做完，单元测试全绿：打码框的位置算得准，静止帧上看也严丝合缝。

然后我把成片导出来，从头到尾看了一遍。**画面放大的那几秒，马赛克没跟上，邮箱和一串 sk- 开头的密钥明明白白地露在屏幕上。**竖屏改版的裁切里也露了一次。单测测的是「打码框的坐标对不对」，而我真正要的是「成片里认不出敏感信息」——这两件事不是一回事，中间隔着放大、倾斜、裁剪和编码。

从那天起我给这个软件加了一道别的录屏工具基本没有的东西：导出之后，回读成片本身做一次体检，用文字识别一帧一帧看过去，确认该盖住的确实盖住了。这段记录写于 1.0.2 时期；当前发行版本见上方。

顺便说说录屏工具这门生意的钱从哪来，这决定了它们把力气花在哪。常见的做法是：免费版给你加水印或者限时长，把「导出」做成收费闸；或者干脆做成云端服务，你把屏幕内容传上去，按存储和导出计费。屏幕录像是隐私浓度最高的一类素材——里面有你的邮箱、路径、token、没关掉的聊天窗口，受益的是拿走这些素材做存储和转码生意的一方，代价落在传上去的人身上。这套剧本在桌面软件里演过很多遍：买断版停更，功能一点点挪进订阅。

我做黑粉录屏图什么？说实话：**我自己每周要出片，录屏是主力素材，而我不想把屏幕内容交给任何服务器。**它没有订阅、没有云端、不卖存储，所以也没有靠你变现的路径；维护成本落在我自己身上。1.0.2 起导出完成时会附一张赞助码，给愿意的人留个出口，赞助与否功能完全一样。你据此可以判断：它不会为了赚你的钱变糟，但也可能因为我顾不上而停更。

  • 整个屏幕、某个窗口，或者手动框选任意区域——框选的时候单击一个窗口就直接取它的范围，不用自己对边；可以锁 16:9、9:16、1:1、4:3，录竖屏内容不用事后再裁。框选支持 macOS 和 Windows。

✂️ 剪辑时间线：按达芬奇的样子排

🛡 自动打码：本机识别，跟着画面走

打码这件事真正麻烦的不是识别，是跟随。识别出邮箱只是第一步，接下来画面会放大、会倾斜、会被裁成竖屏、页面还会滚动——马赛克得跟着一起动，慢一帧就是一次泄露。

  • 本机识别邮箱、手机号、证件号、银行卡号、密钥和你自定义的关键词（自动识别目前是 macOS），证件号和银行卡号先做校验，误报少。
  • 打码跟随放大、倾斜、裁剪和竖屏改版。页面滚动时，框一段一段跟着文字走，只盖文字经过的那一小块——1.0.1 之前是一个框罩住文字经过的整条路，最坏能盖掉半个画面，这次顺手修了。
  • 导出时如果你临时关掉了标注或缩放轨道，打码轨道始终保留并提示你——这条是故意不给关的。

🩺 成片体检：不信过程，只认成品

回到开头那个坑。教训是：**过程里的检查再绿，也不等于成品是对的。**所以导出完成后可以一键对成片本身做体检，检查项都落在「成品」上：

  • 响度与真峰值：给出输出音量建议，不用自己拿耳朵猜
  • 无声段落和黑屏段落：一段一段标出来
  • 画面卡住：成片停住了但原片还在动——这是导出出错最典型的样子
  • 成片比时间线短：片段超出素材长度，直接定位到素材用完的那一刻
  • 字幕和标题放不下：被裁掉或超出画面的都标出来
  • 文字识别回读画面：逐帧确认敏感信息没有露出（目前 macOS）

  • 平台能力不同：Mac为1.8.0，Windows与Linux为1.8.0；人声隔离、自动打码里的敏感信息识别和成片文字回读目前仅 macOS。框选时「单击窗口取范围」支持 macOS 与 Windows。Windows／Linux 的桌面交互仍需对应系统实机核验。
  • Linux 依赖多：录屏全部经 xdg-desktop-portal，还要 Vulkan 驱动和对应桌面的 portal 后端。

🧭 我的判断

如果你也做教程、评测、软件演示这类内容，录屏的真正成本从来不在录那十分钟，而在后面：删停顿、打码、转竖屏、检查有没有翻车。这个软件的全部设计重心都在「录完之后」，包括那道听起来有点笨的体检——导出完再看一遍成片。

笨办法有笨办法的好处：它不相信我自己写的任何一个中间步骤，只认最后那个文件。经历过「单测全绿但邮箱露出来」之后，我觉得这个不信任是值得的。这次给这篇文章拍截图，我又被自己的软件教育了一遍：拍图的时候看出来三个问题——切分片段会丢掉后面的音乐、滚动页面上的打码框太大、静音被转写成「[BLANK_AUDIO]」这样的英文标记——都是测试没抓到、画面一看就明白的。修好了才出 1.0.1。1.0.2 加赞助码时又来了一次：我写的 14 项实机检查全部通过，截图一看，赞助条卡在导出对话框的底边，只露出半行字，按钮在底边以下，点开的码也落在看不见的地方。检查问的是「它在不在」，用的人要的是「看不看得见」。
